Opening the start form of a campaign moves the form twice within its first second:

1. The section with the target is drawn empty, then filled: everything below moves down (61 px at
   960x1080 in R-02).
2. The suggestions of "environments" and "kpis" are drawn once their reads have answered: each of
   the two fields grows by 33 px and moves the fields below it.

A probe that reads the browser's `layout-shift` entries with their sources, one run per viewport,
gave per page load a sum of 0.032 to 0.050 with the theme of R-01 and 0.042 to 0.057 with the theme
of R-02: the labels and suggestions are larger since UXF-017 closed, so late content is taller.

The page checks count only the shifts after the page reports ready (`main` without a loading mark).
The second movement lands within about 25 ms of that mark, before it in one run and after it in the
next. So the number measured on unchanged input is not one number:

| input | `layout_shift.after_ready@1` of the start form, per run |
|---|---|
| R-01 as recorded | 0.0151 |
| the document and theme of R-01, measured again for R-02 | 0.026 |
| the theme of R-01, 4 more runs | 0.0129, 0.0208, 0.0208, 0.0129 |
| R-02 | 0.0176 |
| the theme of R-02, 5 more runs | 0.0284, 0.0176, 0.0284, 0.003, 0.0284 |

`page_checks.layout_shift.max` of a round is this page's value in all three rounds. A ratchet on it
with the skill's tolerance of 0.01 would fail and pass on the same input.
`docs/browser-adapter.md` reports the same of another site: sampled layout shift values vary from
run to run.

Cause, read in the generated runtime (`src/runtime/fields.tsx`, `TagsInput`): the element that holds
the suggestions does not exist until there is one to show, so no rule of the theme can keep its
place free. That is the stock generator's: a known loss candidate. What the studio can do in its own
document: put the target beside the form, not above it, so the first movement does not reach the
form.

Heuristic 4 (stable layout): partial.

Triage: frequency 1 of 11 scenarios (start-campaign), confidence 2 (the page checks and the probe
agree), cost L. Priority 0.05.

Fix in one line: keep the place of late content free before it arrives, and measure the shift of
this page over several runs.

(UXF-004), which moves nothing as the page loads.

## Closed in R-04: the page was fixed, and the measure is taken five times

What moved after ready, read from the browser's `layout-shift` entries with their sources and the boxes
of the form frame by frame (a scratch probe on R-03's build):

1. the target above the form is drawn as a loading skeleton 107 px tall and then as its three fields,
   167 px: the form moves 61 px down;
2. the suggestions of "journeys", "environments" and "kpis" arrive after their reads, 33 px each;
3. the form itself shows an empty loading bar (`.ui-skeleton`, `role=status` without a label) above
   its fields while it loads its values; when it goes, every field moves 11 px up. That bar has no
   `aria-label=Loading`, so the page's ready condition does not wait for it.

The page was fixed, in `themes/studio.css` alone: the target holds the height of its three fields from
the first frame (11rem), each of the three fields with suggestions holds the height of one row of them
(5.75rem), and a form's loading bar lies over the form's top edge (`position: absolute`) instead of
above its fields. The measurement is unchanged (the same ready condition and settle time as R-01 to
R-03), and it is now taken five times: `round.sh` runs the page checks four more times
(`UXUI_ROUND_REPEATS`), and `summary.mjs` reports every page's value per run.

| input | `layout_shift.after_ready@1` of the start form, 5 runs | of the live climb, 5 runs | largest spread of a page |
|---|---|---|---|
| R-03's document and theme (`R-04/before.round.json`) | 0.0284, 0.0176, 0.0176, 0.0176, 0.0284 | 0.013, 0.0009, 0.0009, 0.013, 0.013 | 0.0121 (the live climb) |
| R-04 | 0, 0, 0, 0, 0 | 0.0075, 0.0064, 0.0075, 0.0051, 0.0075 | 0.0024 (the live climb) |
| R-04, a first run before a card was corrected (not kept) | 0, 0, 0, 0, 0 | 0.0075 in each | 0 |

The live climb's value in R-03's input was the step table growing as a live step arrived and moving
"Frontier now" at 960x1080 (UXF-022). In R-04 the step table is the last section and that value is
0.0004. What is left, 0.0051 to 0.0075 at 1366x768, 1280x720 and 1366x657, is the step table's
head: "frontier size" breaks onto a second line once the rows arrive and the table sets its column
widths, and the rows move 17 px down.
