# Round: the stock generator against an application's own generator

Status: plan, 2026-11-24. The owner's position, passed on the same day: a UI generated from `ess-ui/1` is
hard to adjust visually and functionally; most applications will write their own generator from the specs.
An earlier admin-console rewrite on generated UI went through many slow back-and-forth cycles to adjust and
extend it. This round measures both ways and states what each needs from `ess-ui/1`.

Case studies: the studio of this repository (`ess/ui/studio.ui.yaml`), and the first live consumer, slot's web
UI, which moves from a hand-written app to React generated by `ess generate ui` with hand-written code only in
declared host slots. slot logs each point where the generated code gets in the way in
`docs/design/ess-ui-friction.md` of its repository.

## The measure

**Cost of an adjustment**: for a fixed list of typical change requests (move a column, sort a list, a custom
cell, a chart axis, a brand theme, a new field end to end, a bespoke widget), the time, the files touched and
the lines changed until the change is visible and its `ess-ui-test/1` tests pass. Measured on both ways, on
the same pages.

## Stories

1. **Friction ledger.** One record per friction point: page and node path, the change asked for, what the
   generator did, the workaround (spec change, generator option, host slot, fork), its cost. The same format
   as slot's file; uxui merges both sources.
2. **Studio on the stock generator.** Generate the studio (`ess generate ui --target react --model ess
   --fixtures`), run it, record its friction points. First findings below.
3. **Change list.** The fixed list of typical change requests above, each with its acceptance as an
   `ess-ui-test/1` step, so both ways are scored on the same list.
4. **An own generator, smallest form.** A generator in Rust that reads the studio document and its model and
   writes one page (the live climb). Records what it has to re-implement because ESS does not hand it over
   (resolution of defaults and references, model binding, live channel semantics, fixture semantics).
5. **Both ways on the change list.** Apply the change list to the stock output (spec edits, generator options,
   host slots) and to the own generator; record the cost of each adjustment.
6. **slot case study.** Classify each slot friction point as it lands: fixed by a spec change, needs a
   generator option, needs a host slot, needs an own generator.
7. **What `ess-ui/1` needs, per way.** From 4 to 6: the requirements on the format for the stock way
   (extension points, theming, per-node overrides) and for an own generator (a resolved, versioned,
   machine-readable form of the document; a conformance suite every generator can be held to, from
   `ess-ui-test/1`). Each goes to the ESS maintainers as a story.

## First findings (story 2, the studio on `ess` 0.98.0)

- F1 **A line chart plots rows in arrival order.** The generated chart places each point by its row index
  (`runtime/composites/chart.tsx:47`); `x` is only a label, and `chart` has no `sort`. Rows inserted by the
  live channel come first, so the climb's x axis reads 5, 4, 1, 2, 3. Needs: a declared order on charts, kept
  by live inserts (sent to the ESS maintainers as a draft story, 2026-11-24). The step table beside it has the
  same symptom, but there the studio document is at fault: `collection` has `sort`, the document does not
  declare it.
- F2 **Structured values print as JSON: the studio document's fault.** The budget and the KPI values are
  declared `as: json`; `ess-ui/1` offers `as: map` and `as: list`. Fix in `ess/ui/studio.ui.yaml`.
- F3 **No resolved form for an own generator.** `ess ui load` prints a summary line ("9 pages, 246 addressed
  nodes"); there is no machine-readable resolved document. An own generator has to parse the YAML and
  re-implement resolution itself. Needs: `ess ui load --format json`, versioned, with the model bindings
  resolved (sent to the ESS maintainers as a draft story, 2026-11-24). Their fit review: the loader fills in
  no defaults today, and several defaults live only in each renderer and already differ between them (read in
  the code, not run: without `reads.filter` the React runtime inserts a live row while the reader is paged
  away, where the schema's default is `count_new`). The draft recommends that the loader fill in every
  default, which would give every generator, stock or own, the same input.
- F4 **Series colours are not distinct.** Three of the chart's four series share one colour. Solved in
  uxui, not in ESS: `themes/studio.css` sets the generated app's CSS variables and adds a series palette,
  shadows, hover and focus. It is one file linked after the generated stylesheet; the generated sources are
  untouched, but the link line in the generated `www/index.html` is an edit to generated output.

- F5 **The generated app owns `data-theme`.** Its runtime (`runtime/theme.ts:12`) writes `data-theme` on
  `<html>` from the document's `theme:` choice, so a host theme that keys its dark mode on the same attribute
  is overwritten on load. The uxui theme keys its modes on `data-uxui-mode`. Every theme a host adds over
  generated output has to learn which names the generator already uses; nothing declares them.

## slot case study (story 6), 2026-11-24

slot's friction log (its repository, `docs/design/ess-ui-friction.md` at commit 04ef0d8 of branch
`ess-ui-job-views`): 18 entries on the job list and job detail. The stock React generator ran about 45
minutes, 20 of them lost to friction, and was dropped at its F5: a job id drawn as `61,259` with no way in the
spec to change it. slot then wrote its own generator (Rust, reads `ess-ui/1` and `ess-http/1` with serde,
emits Vue pages onto hand-written components); 5 entries (F14-F18) remain with it, and reading the YAML
without a resolved form cost about 900 lines (its F16, our F3).

Classification of slot's 13 gap stories (its `docs/design/ess-ui-gaps.md`):

- **Format or model gaps, for ESS**: G1 (a view route reads a member of a larger answer), G2 (a `Binary64`
  literal in `sets`), G6 (local time beside UTC), G7 (one host component at several places), G8 (a search over
  several fields), G10 (a value derived from two fields and the clock), G13 (a read-only entity without
  invented commands), the event stream that `ess-http/1` cannot declare (its F18), and `tone_by` on a badge
  (the semantic half of G11). G12 is our F3, already filed.
- **Value rendering of the stock generator, for ESS**: G3 (an integer id drawn with grouping), G4 (`as: list`
  joined by commas), G5 (`as: map` draws a tagged union as raw JSON). Wrong output, not styling.
- **Styling and layout, for uxui themes and templates, not ESS**: G9 (column widths, one-line cells, class
  hooks), its F9 (label beside value), the colour per value of G11.

Result for the standing question: slot chose its own generator after 45 minutes on the stock one, which
matches the owner's observation. Both ways still need the resolved document (P0 3 of `docs/ess-gaps.md`).

## Studio: own generator (stories 3-5, 2026-11-24)

Measured in worktree `uxui-own-gen` (`docs/change-list.md`, `docs/own-generator.md`, crate `generators/own`,
no third-party crates). Decision for the studio: **own generator**, under two conditions: the own page is held
to `ess/ui/tests/studio.yaml` through a browser run, and ESS ships the resolved document plus a conformance
suite every generator runs. If ESS refuses either, reassess.

- Durability: on the stock way 4 of 10 change items need edits to generated code, which every
  `ess generate ui` overwrites (it happened 4 times in the spike), and 4 need host slots. On the own way all
  10 are generator or spec edits.
- Cost per change: the same order on both ways (0.1 to 0.7 agent minutes per item).
- Price: one page cost 1,807 lines, 3 of 12 composites; 1,296 of them re-implement what ESS does not hand
  over, about 960 of which a resolved document with model bindings would remove.

## Standing question

For each UI in this round, and again whenever the numbers change: stock generator or our own? The owner's
observation is that owning the generator was usually the better path. Story 5's adjustment costs decide it
per UI, and the decision with its reason goes into this file.
